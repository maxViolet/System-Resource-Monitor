## C1 evidence

The executable was started directly from a neutral `%TEMP%\b12-claude\` working directory. Fixed arguments were `--safe-mode --tools "" --no-session-persistence --print --output-format json "/usage"`; there was no input message beyond `/usage`, no settings file, and a 45-second timeout. The probe captured stdout and stderr separately with no shell window. It did not use `claude -p` for model work.

Two consecutive polls began at 14:51:56 and 14:53:16 UTC. They completed in 3.2 and 2.5 seconds, with zero stderr bytes, `is_error: false`, `local_command: "usage"`, `num_turns: 0`, `duration_api_ms: 0`, and zero input/output tokens. Each included both observed window rows and reset text. The JSON result envelope also carries session and run identifiers, which are omitted here. Sanitized window excerpt:

```text
Current session: 100% used · resets Oct 20, 8:59pm [local timezone]
Current week (all models): 95% used · resets Oct 21, 2:59am [local timezone]
```

For signed-out behavior, a new empty `CLAUDE_CONFIG_DIR` was created. `claude auth status --json` returned exit code 1, `loggedIn: false`, and `authMethod: none`. The same C1 invocation then returned `is_error: false`, `subtype: success`, `local_command: "usage"`, and 206 characters of local session statistics, with no percentage or reset row and no sign-in error. The real account was not signed out. Without a separate auth-status operation, that output is an unknown shape rather than a trustworthy sign-in classification. Offline and child-proxy failures were not induced after the candidate already failed the stable-contract and signed-out gates; network classification remains unverified, not passed.

Ten C1 polls began at 14:55:08 through 15:04:09 UTC, 60 seconds apart. They took 2.2–2.7 seconds each. All returned 100% and 95% used, zero model turns, zero API time, and zero reported cost. Transcript filenames were compared before and after every poll; no new transcript appeared. The user confirmed account-work isolation. The reset rendering split evenly:

| Polls | Short reset shown | Weekly reset shown |
|---|---|---|
| 1, 7–10 | Oct 20, 21:00 local | Oct 21, 03:00 local |
| 2–6 | Oct 20, 20:59 local | Oct 21, 02:59 local |

No reset boundary occurred during the run. The visible one-minute difference is not explained by an official precision rule, so the exact reset time cannot be handed to B013. The official output exposed integer used shares only. `100 − used` would give 0% and 5% remaining, but no non-integer sample or official rounding contract was established; rounding reconciliation is unverified.

The independent interactive reading showed `Current session` 100% used, resetting at 21:00, and `Current week (all models)` 95% used, resetting on Oct 21 at 03:00 (Asia/Qyzylorda). C1 at 15:15:24 UTC completed in 2.4 seconds with those same two rows, used shares, and displayed reset times. It again had zero model turns and API time. This is one matching sample, not a documented precision or rounding rule; the earlier ten-poll drift remains.
