## Outcome

The `app-server` command itself is labelled `[experimental]` in `codex --help`, and the official app-server documentation says that "the app-server command and WebSocket transport are experimental and aren't supported for production workloads." Plan step 3a fails C1 only for an experimental or undocumented method, so C1 passes. The user decided on 2026-10-19 to accept C1 with constraints: B012 pins the tested client versions and treats any other version or response shape as unavailable.

## Accepted contract

### Invocation

Start `codex.exe` directly with the fixed arguments `app-server --listen stdio://`, `UseShellExecute=false`, and a neutral working directory. Write three newline-terminated UTF-8 JSON messages to stdin:

```json
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"clientInfo":{"name":"b10-probe","version":"0.0.1"},"capabilities":{"experimentalApi":false}}}
{"jsonrpc":"2.0","method":"initialized"}
{"jsonrpc":"2.0","id":2,"method":"account/rateLimits/read","params":{"excludeResetCreditDetails":true}}
```

Read stdout line by line until the response with `"id":2`, then close stdin. The process exits with code 0 within 10 seconds. `excludeResetCreditDetails: true` is the documented flag for background usage polls. Never send `account/rateLimitResetCredit/consume`: it consumes a reset credit.

The probe harness was an ad hoc PowerShell script (`System.Diagnostics.Process`, redirected stdin, stdout, and stderr, 60-second timeout). It was not committed.

### Response schema

Source: `codex app-server generate-json-schema --out <dir>` from the qualified binary, without `--experimental`. The method appears in `ClientRequest.json`. The response type is `v2/GetAccountRateLimitsResponse.json`.

- `rateLimits` (required): `RateLimitSnapshot`, the backward-compatible single-bucket view.
- `rateLimitsByLimitId`: object or `null`, a map from metered `limitId` to `RateLimitSnapshot`. Only `codex` was observed.
- `RateLimitSnapshot`: `limitId`, `limitName`, `planType`, `primary` and `secondary` (each `RateLimitWindow` or `null`), `credits`, `individualLimit`, `rateLimitReachedType`, `spendControlReached`, `normalModelSlug`. All fields are nullable.
- `RateLimitWindow`: `usedPercent` (`int32`, required), `windowDurationMins` (`int64` or `null`), `resetsAt` (`int64` or `null`, Unix seconds, UTC).
- Other top-level fields: `ordinaryUsageAllowed` (boolean or `null`; `null` means unavailable), `rateLimitResetCredits`, `rateLimitUpsell`, `accountId`. B012 must ignore and never log `accountId`.

Sanitized response, from the first of the ten polls:

```json
{"id":2,"result":{
  "ordinaryUsageAllowed":true,
  "rateLimits":{"limitId":"codex","limitName":null,"normalModelSlug":null,
    "primary":{"usedPercent":0,"windowDurationMins":300,"resetsAt":1792450500},
    "secondary":{"usedPercent":10,"windowDurationMins":10080,"resetsAt":1792997947},
    "credits":{"hasCredits":false,"unlimited":false,"balance":"<redacted>"},
    "individualLimit":null,"spendControlReached":false,"planType":"plus","rateLimitReachedType":null},

  "rateLimitResetCredits":{"availableCount":"<redacted>","credits":null},

```

Before the response, stdout carries the `initialize` result and notifications (`remoteControl/status/changed`, and `account/updated` with `authMode` and `planType` when signed in). The parser skips them.

### Limit windows

| Field | Window | Duration | TUI label |
|---|---|---|---|
| `primary` | Short window | 300 minutes | `5h limit` |
| `secondary` | Weekly window | 10080 minutes | `Weekly limit` |

On plan `plus` the set has one short window and one weekly window, and the weekly window is the binding weekly window. Identify windows by `windowDurationMins`, not by position. A bucket other than `codex` in `rateLimitsByLimitId` is outside this contract.

### Reset time

`resetsAt` is Unix seconds in UTC. Converted to local time, every value matched the TUI display to the minute (table under criterion 5). While a short window has 0 % used and has not started, `resetsAt` is "now + 300 minutes" and moves forward with every poll. After usage starts the window, it stays fixed.

### Rounding

`remaining = 100 − usedPercent`. The app-server already rounds the used share to an integer: at tag `rust-v0.159.0` (commit `687a119f0fcaace47e1f1abcc77cec6c813fd6da`), `codex-rs/app-server-protocol/src/protocol/v2/account.rs` converts the core `f64` with `used_percent: value.used_percent.round() as i32` (Rust `round`, half away from zero). The TUI computes `(100.0 - percent_used).clamp(0.0, 100.0)` from the same core `f64` and prints it as `{percent_remaining:.0}% left` (`codex-rs/tui/src/status/card.rs`, `codex-rs/tui/src/status/rate_limits.rs`). Both give the same integer, except when the core used share is exactly `x.5`. Then the TUI can show one point more than `100 − usedPercent`. All observed samples were integers (0 and 10), so this tie case is unverified on a live account.

### Failure classification

| Condition | How produced | Envelope from `account/rateLimits/read` | Time to failure | Exit code / stderr |
|---|---|---|---|---|
| Success | Signed in, online | `result` with `rateLimits` of the schema shape | 0.83–2.0 s (19 polls) | 0 / 0 bytes |
| Signed out | `CODEX_HOME` set to a new empty temp directory | `{"code":-32600,"message":"codex account authentication required to read rate limits"}` | 0.44 s | 0 / 256 bytes (warning that helper binaries are not created under a temp `CODEX_HOME`) |
| Network failure, offline | Wi-Fi off, no physical adapter up | `{"code":-32603,"message":"failed to fetch codex rate limits: error sending request for url (…)"}` | 0.25 s | 0 / 0 bytes |
| Network failure, proxy | `HTTPS_PROXY=http://127.0.0.1:9` for the child only | Same `-32603` envelope | 2.3 s | 0 / 0 bytes |
| Unknown format | — | Anything else: a different code or message, a `result` without the schema shape, or no `id` 2 response before the timeout | — | — |

Signed-out and network failures differ in the structured `code` field. Both codes are generic JSON-RPC codes, so the classifier also pins the message: `-32600` with the exact signed-out text is sign-in failure, and `-32603` with the prefix `failed to fetch codex rate limits:` is network failure. Every other error is unknown format. The `-32603` path can also cover backend HTTP errors; B012 treats them as network failure. Neither failure mode hung the client.

### Latency

The 19 successful polls took 0.83–2.0 seconds from process start to the response, median 0.96 s. B012 needs a timeout well above 2 s; the probe used 60 s and never reached it.

### Constraints

- **Login:** the client uses its own saved ChatGPT login. The mechanism never reads it.
- **Network:** the client calls its usage endpoint for every read; the bar does not call it.
- **Version pin:** qualified on `codex-cli 0.159.0` only. The standalone client updates itself (`auto-update-version`), and the npm client is already at 0.163.0. B012 must accept only versions it has verified and treat any other version as unavailable.
- **Experimental command:** `app-server` is labelled experimental and not for production. This is the risk recorded in the outcome.
- **Client choice:** qualify the signed standalone executable. The npm shim is an unsigned script client and needs explicit user consent under [Provider adapters](../../implementation-plan.md#provider-adapters).
- **Local side effects:** each poll starts a full app-server, which writes the client's own local state databases under `CODEX_HOME`. It creates no session file.

## Unverified items

- Access revoked on a live account: not tested safely.
- A used share that changes after a task: the task did not move either integer percentage. Freshness was shown through the start of the short window instead.
- The `x.5` rounding tie between `usedPercent` and the TUI display.
- Windows other than `codex`, other plan tiers, and other client versions, including the npm client 0.163.0.
- Backend HTTP errors other than network loss: assumed to use the same `-32603` path.
